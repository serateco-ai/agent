# 화면 개발·브라우저 검증

화면·CSS·JS·템플릿·화면 데이터·연결 API·인증 흐름 등 사용자 화면에 영향을 주는 수정에 적용한다.

## 구현

- 기존 레이아웃·디자인·컴포넌트·공용 입력/주소/에러 유틸을 먼저 확인하고 재사용한다. 화면별 복붙·새 프레임워크로 임의 교체하지 않는다.
- 정적 리소스 변경은 프로젝트 캐시 갱신 규약을 따른다. preload·script·style 등 관련 참조를 함께 갱신하고 브라우저가 새 파일을 받는지 확인한다.
- 유효한 HTML 구조, 템플릿에서 접근 가능한 이름, 중복되지 않는 row-key를 사용한다.
- 목록은 서버 페이징이 기본이다. 페이지 변경은 재조회하며 총건수는 서버 응답을 사용한다. 대량 전량 로드 후 slice 금지. 명시된 프로젝트 예외만 유지한다.
- 목록·COUNT·다운로드는 같은 검색 조건을 쓴다. 전체 선택·엑셀은 화면의 현재 페이지 배열로 전체를 대체하지 않는다.
- 값의 출처가 불명확하면 `알수없음`으로 명확히 표시한다. 임의의 0·대시·더미를 실제 값처럼 채우지 않는다. 정상 0건·조회 실패·미확인 상태를 구분한다.
- 서로 다른 업무 상태·집계 기준을 이름이 비슷하다고 합치지 않는다. 서버가 기간·조건을 정규화하면 화면도 실제 적용 조건을 표시한다.
- 비동기 응답 역전으로 이전 검색·탭 결과가 최신 화면을 덮지 않게 한다. 로딩·실패·빈 결과·재시도 동작을 확인한다.
- 기존 공용 모달과 확인 흐름을 사용한다. native alert/confirm/prompt로 임의 대체하지 않는다. 팝업·중첩 모달의 포커스와 사용자 제스처를 확인한다.

## 완료 조건 — 실제 브라우저 테스트 필수

1. 변경본이 실제 실행 환경에 반영됐는지 확인한다. 프로젝트의 표준 진입 URL과 정상 인증 흐름을 사용한다.
2. 실제 브라우저에서 수정 화면을 열고 변경 동작을 클릭·입력·조회·저장 등으로 끝까지 실행한다. 코드 읽기·빌드·curl·SQL만으로 대체하지 않는다.
3. 영향받은 정상/실패/빈 상태와 관련 흐름을 확인한다. 반응형 수정은 대상 화면 크기에서도 확인한다.
4. 브라우저 콘솔·네트워크에서 렌더 예외·실패 요청·오래된 리소스·계속되는 로딩을 확인한다. 관련 API/서버 로그와 대조한다.
5. 다운로드/인쇄를 수정했다면 실제 생성 파일과 내용을 확인한다. 권한을 수정했다면 UI 가림과 별도로 API 직접 호출 거부를 검증한다.
6. 발견한 회귀를 수정하고 해당 흐름을 재검증한다. 증거는 개인정보를 제외한 캡처·응답·로그 요약으로 남긴다.

보고에 **실제 URL/화면 · 수행 동작 · 통과/실패 · 콘솔/네트워크 문제 · 미검증 항목**을 적는다. 도구·서버·계정 문제로 브라우저 검증이 막히면 “수정 반영, 브라우저 미검증”으로 보고한다. 화면 작업 전체를 완료/성공 처리하지 않는다.
