# 작업·검증·보고

1. 대상·요구 항목·적용 지침·현재 변경을 확인한다. 기존 이력은 참고하되 현재 소스와 환경을 대조한다.
2. 원인을 재현하거나 근거로 좁힌 뒤 필요한 범위만 수정한다. 실패의 후속 증상을 근본 원인으로 단정하지 않는다.
3. 프로젝트에 정의된 빌드·실행·검증 절차를 사용한다. 명령을 관례로 추측하지 않는다.
4. 변경에 맞는 검증을 실행한다. 소스·타입·빌드 검증과 실행 검증을 구분하며, 화면 변경은 ui.md를 따른다.
5. 요구 항목 누락·경로 및 계약 변경·가드 회귀·관련 사본·직접 수정분 보존을 검토한다.
6. 실패를 수정하고 영향받은 검증을 다시 실행한다. 통과한 무관한 검증을 이유 없이 반복하지 않는다.
7. 변경 파일·주요 동작·검증 수단/결과·남은 문제를 짧게 보고한다. 정상 로그·코드 전문 덤프 대신 필요한 근거만 제시한다.

검증 불가는 완료가 아니다. 실패/미검증 항목, 막힌 이유와 재검증에 필요한 조건을 적는다. HTTP 200·컨테이너 Up·빌드 성공 하나로 기능 정상이라 판정하지 않는다.

리뷰는 신규 회귀 / 기존 결함 / 이미 추적 중인 범위 밖 문제를 구분한다. 실제 호출·상태 전이·권한·잠금·커밋 순서를 확인하고 의도된 정책을 결함으로 단정하지 않는다. 다른 에이전트·외부 검토의 결론도 원문·코드·로그와 대조한다. 특정 도구나 다른 에이전트의 검토를 모든 작업의 필수 단계로 고정하지 않는다.
